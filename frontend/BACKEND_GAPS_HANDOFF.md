# مراجعة تكامل الواجهة والـ Backend

مراجعة ساكنة للكود الموجود في `frontend/app/src` مقابل الـ controllers والـ models الحالية. القائمة تركز على الوظائف التي تطلبها الواجهة ولا تجد API مكتملًا، أو التي تحفظ حالتها في المتصفح فقط.

## المطلوب من مهندس الـ Backend

### 1. API القوالب — غير موجود حاليًا

الواجهة تستخدم `GET /api/templates` و`PUT /api/templates` في `app/src/services/templateService.js`، ولا يوجد Controller لهذا المسار. حفظ القوالب أو مشاركتها بين المستخدمين لن يعمل على الخادم.

المطلوب:

- إضافة قراءة وحفظ للقوالب في قاعدة البيانات، مع حماية الصلاحيات المناسبة.
- حفظ بيانات القالب: `id`, `code`, `name`, `description`, القسم، `isDefault`، قائمة المهام وترتيبها، الأقسام المسؤولة، والمهام الإضافية إن كانت جزءًا من القالب.
- إرجاع القالب الأساسي `temp1` حتى لو لم تُنشأ قوالب أخرى.

الواجهة المتأثرة: `app/src/hooks/useTaskTemplates.js` و`app/src/components/engineer/TaskTemplatePicker.jsx`. يوجد مكوّن أقدم منفصل `TaskTemplatesPanel.jsx` يستخدم أيضًا `templatesService.js`.

### 2. API الأقسام المسؤولة — غير موجود حاليًا

`app/src/services/departmentsService.js` يطلب:

- `GET /api/responsible-departments`
- `POST /api/responsible-departments` مع `{ name }`

لا يوجد Controller لهذا المسار في النسخة الحالية. في وضع البيانات الحقيقية، إضافة قسم جديد أو جلب قائمة الأقسام لن تُحفظ على الخادم؛ وضع الـ mock يخزن الإضافات في `localStorage`.

المطلوب: جدول للأقسام، قراءة قائمة موحدة، إضافة اسم جديد دون تكرار، وربط صلاحية الكتابة بمدير القسم. قيم القسم المختارة على المهمة نفسها تُرسل حاليًا في `Department`، لكن **مصدر قائمة الأقسام** غير متزامن بين المستخدمين.

### 3. API سجل النشاط — غير موجود حاليًا

`app/src/services/activityService.js` يطلب:

- `GET /api/dashboard/activity` مع فلاتر `types`, `teamId`, `engineerId`, `q`, `from`, `unreadOnly`, `cursor`, `limit`.
- `GET /api/dashboard/activity/unread-count`.
- `POST /api/dashboard/activity/read` مع `{ ids }` أو `{ all: true }`.

هذه المسارات غير موجودة في `DashboardController`. الموجود في `SecurityController` هو `/api/security/audit`، وهو سجل تدقيق مختلف ولا يطابق عقد صفحة النشاط.

المطلوب: تخزين أحداث نشاط قابلة للقراءة والترقيم، مع هوية الفاعل والفريق والمشروع ونوع الحدث والبيانات الوصفية، بالإضافة إلى حالة القراءة لكل مدير/مستخدم. يجب أن تغطي الأحداث التي تعرضها الواجهة مثل تغييرات المهام والمشاريع والجولات والحصر والملفات والأرشفة والفرق.

### 4. استكمال API الأرشيف — جزئي حاليًا

الموجود:

- `GET /api/dashboard/archives` يعيد بيانات ملخصة فقط.
- حذف المشروع الجاري عبر `DELETE /api/dashboard/engineers/{engineerId}/projects/{projectId}` ينشئ سجل أرشيف ويحفظ `SnapshotJson` في قاعدة البيانات.

الناقص:

- مسار تفاصيل مثل `GET /api/dashboard/archives/{id}` يعيد لقطة المشروع كاملة، بما فيها المهام القياسية والإضافية وحالاتها ومواعيدها وملاحظاتها والجولات/البيانات المرتبطة اللازمة للعرض والاسترجاع. القائمة الحالية لا تعيد `SnapshotJson`، لذلك Drawer الأرشيف لا يستطيع عرض التفاصيل.
- `POST /api/dashboard/archives/{id}/restore` لاسترجاع اللقطة إلى المهندس، مع معالجة حالة عدم وجود المهندس أو اختيار مهندس بديل.
- `DELETE /api/dashboard/archives/{id}` للحذف النهائي من الأرشيف.

ملاحظة تكامل: صفحة `ArchivesPage.jsx` تستدعي `getEngineerData`, `putEngineerData`, و`deleteArchive`، ولا تظهر لهذه الدوال تعريفات أو imports داخل `app/src` حاليًا. يلزم إصلاح هذه الوصلات في الواجهة بالتوازي؛ إضافة endpoints وحدها لن تكفي إذا ظلت الدوال غير معرفة.

### 5. حقول مواعيد المشروع والمهمة — الـ API الحالي لا يحفظها كاملة

الواجهة تتيح تاريخ بداية المشروع (`startDate`)، وتاريخ بداية كل مهمة، وتاريخ/وقت انتهاء المهمة. الـ DTOs والـ models الحالية لا تشمل هذه القيم كلها:

- `Project` / `ProjectDto`: لا يوجد `StartDate`، بينما نموذج إنشاء المشروع وصفحة المهندس ترسلان `startDate`.
- `ProjectTaskState` و`CustomTask`: يوجد `DueDate` فقط؛ لا يوجد `StartDate` أو `DueTime`.
- `DashboardController` يقرأ ويكتب `dueDate` فقط في المهمة القياسية والإضافية، لذلك أي `startDate` أو `dueTime` ترسله الواجهة سيُهمل عند الحفظ/التحميل.
- لقطة الأرشيف الحالية لا تتضمن هذه الحقول أيضًا.

المطلوب:

- إضافة `StartDate` للمشروع، و`StartDate` و`DueTime` للمهمة القياسية والإضافية، مع أعمدة وترحيل آمن لقواعد البيانات الحالية (SQLite وSQL Server).
- تمريرها في DTOs للقراءة والكتابة وفي لقطة الأرشيف والاسترجاع.
- اعتماد معنى واضح للوقت والمنطقة الزمنية. الواجهة ترسل تاريخًا ووقتًا محليين بصيغة HTML `date` و`time`.

### 6. إشعارات اقتراب موعد المهمة — حاليًا حساب محلي فقط

`app/src/services/engineerAlerts.js` يحسب تنبيهات المواعيد في المتصفح اعتمادًا على بيانات المهندس، ويحدّثها `EngineerAlertsWatcher` كل 45 ثانية. حالة القراءة والأحداث المحلية محفوظة في `localStorage` تحت `tender-eng-alerts:v1:{engineerId}`. هذا ليس إشعارًا محفوظًا أو موحدًا على الخادم، ولا يصل للأجهزة/المتصفحات الأخرى.

الموجود في `/api/notifications` هو جلب إشعارات المهندس وتعليمها كمقروءة. كما ينشئ الـ Backend حاليًا إشعارات عند إنشاء مشروع وعند إكمال مهمة؛ لا يوجد منطق خلفي مجدول لمواعيد المهام أو وقت الانتهاء.

المطلوب المقترح:

- إنشاء إشعار محفوظ عند اقتراب موعد المهمة (مثلًا خلال 24 ساعة) وعند تجاوز الموعد، وفق سياسة يحددها المنتج.
- منع إنشاء إشعار مكرر لنفس المهمة ونفس الموعد، مع إنشاء إشعار جديد إذا تغير الموعد.
- تضمين `projectId`, `taskId` أو معرّف المهمة الإضافية، تاريخ/وقت الاستحقاق، ومستوى التنبيه.
- تشغيل الفحص من خدمة خلفية أو آلية موثوقة، لا من متصفح المهندس فقط.

### 7. حقول مشروع إضافية تحتاج عقد DTO واضح

الواجهة تضيف وتقرأ `templateId` و`templateName` للمشروع، وتضيف metadata مثل `createdBy`, `createdByRole`, وبيانات صاحب/وقت آخر ملاحظة (`noteBy`, `noteByRole`, `noteAt`). هذه الحقول غير موجودة في `ProjectDto` / `ToProjectDto` الحالية، باستثناء وقت الإنشاء الداخلي `CreatedAt` الذي لا يُعاد بهذه الصيغة.

إذا كان المطلوب أن يتذكر المشروع القالب المطبق أو أن تُنشأ إشعارات موثوقة عند إضافة المشروع/تعديل ملحوظته، ينبغي حفظ وإرجاع هذه البيانات أو الاعتماد على سجل أحداث/Notifications خادمي بدل metadata يرسلها المتصفح.

## بيانات/حالات تعتمد على المتصفح حاليًا

- **نشاط مدير القسم:** `useDeptActivity.jsx` يبني الأحداث بمقارنة snapshots للمهندسين والحصر، ويحفظ snapshots والأحداث ووقت المشاهدة في `localStorage`. يختلف السجل والعداد من متصفح لآخر ولا يمثل سجلًا مركزيًا.
- **تنبيهات المهندس المحلية:** عناصر التنبيه وحالة قراءتها في `engineerAlerts.js` محفوظة في `localStorage`؛ تنبيه الموعد نفسه يعاد حسابه من بيانات المشروع ولا يُسجل في Notifications API.
- **قالب المشروع المختار:** `templatesService.js` يحتفظ بـ `project-template:{projectId}` في `localStorage` كحل بديل. كما أن `templateId` الموجود في كائن المشروع لا يمر عبر DTO الحالي.
- **إخفاء عناصر الأرشيف:** صفحة الأرشيف تخزن العناصر المخفية في `localStorage` لأن الحذف/الاسترجاع الدائم غير مكتملين.
- **المشروع النشط:** معرف المشروع المختار محفوظ محليًا (`tender-dashboard-active-project:{engineerId}`)، وهو تفضيل واجهة وليس بيانات عمل، فلا يحتاج عادةً إلى Backend.
- **الجلسة:** `useAuth.jsx` يخزن الدور والمعرف في `localStorage`. إذا كان المطلوب جلسة موثقة وآمنة متعددة الأجهزة، يلزم مراجعة آلية المصادقة/الجلسات على الخادم؛ كلمة المرور نفسها لا تُحفظ في هذا المفتاح.
- **وضع mock:** `USE_MOCK` في `app/src/services/request.js` يساوي true افتراضيًا ما لم يُضبط `VITE_USE_MOCK=false`. الخدمات التي تستخدمه قد تعرض بيانات تجريبية أو تخزن تغييرات في `localStorage`؛ يجب التأكد من إعداد البيئة قبل تقييم عمل الـ Backend.

## مسارات موجودة بالفعل

لا حاجة لإعادة بنائها قبل فحصها؛ الـ controllers الحالية تتضمن:

- `GET /api/bootstrap` و`GET /api/tasks`.
- `GET/PUT /api/roster`، وتحديث ملف المهندس وصورته.
- `GET/PUT /api/dashboard/engineers/{id}`، وحذف مشروع جارٍ مع إنشاء سجل أرشيف.
- `GET/PUT /api/dashboard/hasr/{teamId}`.
- `GET/PUT /api/dashboard/config`، و`GET/PUT/DELETE /api/fields`.
- `GET /api/dashboard/auth`، `PUT /api/dashboard/auth`، و`POST /api/dashboard/auth/hash`، إضافة إلى بعض مسارات الأمن وكلمات المرور.
- رفع/عرض/حذف المرفقات وT Files والجولات والنسخ عبر `/api/files`.
- `GET /api/notifications/{engineerId}` وتعليم إشعار واحد أو الكل كمقروء عبر POST.

## ترتيب تنفيذ مقترح

1. حفظ DTO وDB لحقول `Project.StartDate`, `TaskState.StartDate`, `DueTime` للقياسية والإضافية؛ لأن المواعيد والتنبيهات الحالية تفقد جزءًا من بياناتها بعد الحفظ.
2. إضافة خدمة إشعارات مواعيد موثوقة على الخادم ومنع التكرار.
3. إضافة Templates API وResponsible Departments API.
4. تحديد عقد Activity API وتنفيذه أو توحيد صفحة النشاط مع `/api/security/audit` إذا كان ذلك هو المطلوب.
5. إكمال تفاصيل/استرجاع/حذف الأرشيف وإعادة توصيل دوال صفحة الأرشيف.
